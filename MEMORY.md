# Обоснование выбора системы памяти

## Что мы выбрали

**Гибридную память:**
- **Краткосрочная:** история текущего чата в GroupChat (в оперативной памяти)
- **Долгосрочная:** Markdown-журнал `memory/journal.md` с записями всех сессий
- **Семантическая:** `memory/SOUL.md` — описание ценностей и принципов

## Рассмотренные альтернативы

### 1. RAG (Retrieval-Augmented Generation)

**Как работает:** текст разбивается на чанки, каждый чанк превращается в embedding (числовой вектор), при запросе ищутся ближайшие чанки по косинусному сходству.

**Плюсы:**
- Хорошо работает для больших баз знаний
- Масштабируется на миллионы документов
- Много готовых библиотек (LangChain, LlamaIndex)

**Минусы (почему НЕ выбрали):**
- **Chunking теряет контекст:** разбиение текста на куски по 200-500 токенов разрывает связи между идеями
- **Top-k неоптимален:** всегда берётся фиксированное число чанков, даже если релевантных меньше или больше
- **Нет временной динамики:** векторный поиск не различает «старое» и «новое»
- **Требует embedding-модель:** дополнительный ресурс (либо локальная, либо API)
- **Избыточно для наших объёмов:** журнал сессий — это десятки записей, а не миллионы документов

### 2. GraphRAG (Microsoft, 2024)

**Как работает:** строит граф знаний из документов, где узлы — сущности, рёбра — отношения. При запросе обходит граф.

**Плюсы:**
- Учитывает связи между сущностями
- Отвечает на вопросы «почему», «как связано»

**Минусы:**
- **Сложная реализация:** требует LLM для извлечения сущностей и построения графа
- **Дорого:** много LLM-вызовов при индексации
- **Избыточно** для нашего случая

### 3. Vector-only память (ChromaDB, FAISS, Qdrant)

**Как работает:** все сообщения превращаются в embeddings и хранятся в векторной БД.

**Плюсы:**
- Простая семантическая память
- Быстрый поиск

**Минусы:**
- Нет структуры, только «похожесть»
- Требует embedding-модель
- Не подходит для аудита (что именно было в сессии?)

### 4. Markdown-журнал (наш выбор)

**Как работает:** каждая сессия дописывается в `memory/journal.md` в структурированном виде. При старте загружаются последние N записей.

**Плюсы:**
-  **Прозрачность:** человек читает журнал без инструментов
-  **Аудит:** видно каждую сессию с датой, запросом, ответом
-  **Нет зависимости от embeddings:** не нужна дополнительная модель
-  **Простота:** никаких БД, никаких индексов
-  **Версионирование:** можно коммитить в Git
-  **Совместимо с LLM:** контекст вставляется в промпт как есть

**Минусы:**
-  **Не масштабируется:** при тысячах сессий журнал станет огромным
-  **Нет семантического поиска:** только «последние N»
-  **Линейный рост контекста:** в промпт попадают все последние сессии целиком
-  **Нет забывания:** старые записи не «выцветают»

## Как мы компенсируем недостатки

1. **Ограничение `recall_last(n=2)`** — в промпт идут только 2 последние сессии, чтобы не переполнить контекст 7B-модели.
2. **Возможность ротации:** при >100 сессий журнал можно архивировать вручную.
3. **SOUL.md отдельно** — принципы не смешиваются с историей.

## Что можно улучшить в будущем

Гибридный подход:
- Markdown-журнал для **аудита** и «свежих» сессий (последние N)
- Векторная БД (ChromaDB) для **семантического поиска** по старым сессиям
- Temporal decay: старые записи получают меньший вес
- Hierarchical summarization: старые сессии сжимаются в саммари LLM-ом

Такой гибрид даёт лучшее из двух миров: прозрачность и семантику.
